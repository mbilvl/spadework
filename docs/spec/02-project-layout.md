# 02 — Project layout

Status: Draft · Target: v0.1

A project is a folder. The user owns everything outside `.spadework/`, and the
engine owns everything inside it. Users can keep a project under version
control, which is recommended. `init` sets up a `.gitignore` for the engine
state.

```
acme-fabrication/
├── spadework.toml        # config                       (user)
├── brief.md              # ground truth                 (user)
├── inputs/               # later material               (user, add-mostly)
├── out/                  # the pack                     (engine writes; user may edit)
└── .spadework/           # engine state                 (engine only; gitignored)
    ├── state.json        # per-task fingerprints, status, output hashes
    ├── work/             # raw task outputs (what fix sessions edit)
    ├── records/          # structured session results (JSON)
    ├── runs/<run-id>/    # manifest.json, sessions/*.jsonl, prompts/
    ├── sessions/         # staging directories (temporary)
    ├── control/          # guard policies and settings for live sessions (temporary)
    └── lock
```

## `spadework.toml`

```toml
schema_version = 1

[project]
name = "acme-fabrication"          # slug used in logs and the manifest
playbook = "discovery-website"     # a built-in name, or a path such as "./playbooks/mine"

[models]                           # tasks declare a tier; this maps tiers to models
draft = "sonnet"
review = "opus"

[limits]
budget_usd = 6.00                  # per run
max_time = "2h"                    # per run
rounds = 2                         # review rounds
session_timeout = "25m"

[executor]
name = "claude-cli"
# bin = "/path/to/claude"          # default: SPADEWORK_CLAUDE_BIN, then PATH

[verify]
enabled = true
```

Unknown keys are an error, not a warning, so typos surface in `check`. The
file is validated against a pydantic model, and a JSON Schema generated from
that model ships with the package for editor autocompletion.

## `brief.md`

YAML front matter followed by free Markdown. The front matter is the
machine-readable part. The body is everything else the user knows.

```markdown
---
title: Acme Fabrication — website discovery
reader: A developer scoping a showcase website for a small manufacturer
language: en
currencies: [EUR]
priorities:
  - The product catalogue is the core of the site
  - Non-technical staff must add and edit products unaided
  - Must read as credible to industrial buyers
public_context: >
  A 25-person stainless-steel fabricator in northern Portugal that sells to
  commercial kitchens across the EU. Planning a catalogue/showcase website
  with no e-commerce.
---

# The client
...
```

| Field | Required | Used for |
|---|---|---|
| `title` | yes | Pack title and logs |
| `reader` | yes | Who every document is written for. Injected into the house rules. |
| `public_context` | yes when the playbook has research tasks | The **only** brief content that web-facing sessions see. It may be `""`. Requiring the field makes the user decide on purpose ([07](07-security.md)). |
| `priorities` | when the playbook requires it | The critic checks the pack against them |
| `language` | no (default `en`) | The language the pack is written in |
| `currencies` | no | Money figures are given in each of these |
| any other key | no | Available to templates as `brief.extra.<key>` |

A playbook can declare more required fields (`requires_brief`). `check`
reports any that are missing. A field counts as missing when it is absent,
null, blank, or an empty list.

## `inputs/`

Material that arrives after the brief: call notes, client answers, emails,
and links the client sent.

- v0 accepts UTF-8 `.md` and `.txt` files, in subfolders too. Hidden files
  are ignored. PDF and other document types are **[later]**.
- The recommended naming is `YYYY-MM-DD-topic.md`, so the history reads in order.
- Each file is hashed. Adding, editing or removing a file makes the tasks
  whose `inputs` globs match it stale ([04](04-engine.md)).
- Inputs are staged, read-only, into draft, fix, critic and summary sessions.
  They are **never** given to research sessions.
- Soft limit: 500 KB (500,000 bytes) in total. `check` warns above it.

## `out/` — the pack

```
out/
├── 00-summary.md      # generated by the summary session plus code-rendered tables
├── 01-scope.md        # one document per task, with a Sources section rendered in
├── …
├── sources.md         # every source, grouped by document, with verification status
└── pack.json          # every record, for machines ([06](06-records.md))
```

### Human edits

The engine records a hash of every file it renders into `out/`. If the file's
hash no longer matches at the start of a run, the user has edited it, and the
task becomes **pinned**:

- It is not redrafted and not fixed automatically.
- Other sessions use it as it stands.
- Critic findings against it are reported in the summary for the human to act on.
- `spadework run --force --only TASK` regenerates it after a warning.

## `.spadework/`

Engine-only. The layout above is informational, not a public contract,
except that:

- `runs/<run-id>/manifest.json` has a versioned schema ([04](04-engine.md)).
- `clean` is the supported way to remove state.
- Session logs contain the brief and inputs. They are local files and are
  never uploaded anywhere by spadework.

Staging directories and control files are created per session and deleted
afterwards. `SPADEWORK_DEBUG=1` keeps them for inspection.
